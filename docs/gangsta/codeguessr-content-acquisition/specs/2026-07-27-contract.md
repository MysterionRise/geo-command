# Programme Amendment: Licensed GitHub Content Acquisition

## Objective

Advance the existing “GeoGuessr for code” programme from a synthetic playable demo toward an MVP by adding the smallest trustworthy real-content supply path. A project operator may acquire code from an explicitly approved public GitHub repository at one exact commit, produce immutable and non-publishable review drafts, and feed those drafts into the existing human rights, safety, technical, and publication gates.

The acquisition path may prepare language-mode candidates and narrowly evidenced positive provenance candidates. It is not a general scraper, a gameplay dependency, a publication system, or an AI detector.

## Amendment Authority and Precedence

1. This document is a proposed amendment to the exact approved Programme Contract Revision 6 identified in frontmatter.
2. After all required signatures, this document becomes Programme Revision 7. Revision 6 remains immutable historical evidence.
3. Revision 7 supersedes only the Revision 6 clauses explicitly named in “Superseded Programme Clauses.” Every other Revision 6 requirement, definition, decision, architectural constraint, acceptance criterion, risk control, and negative constraint remains binding.
4. H-001, H-003, and H-004 must each receive a separately signed Revision 2 that cites the exact approved Revision 7 path and SHA-256 hash. Their Revision 1 files remain immutable.
5. H-002, H-005, and H-006 remain at Revision 1 only after each receives the separately signed Revision 7 Compatibility Certificate defined below. A discovered incompatibility blocks implementation and requires a child revision rather than a certificate.
6. This amendment does not authorize implementation. Implementation begins only after Revision 7, all three required child Revision 2 Contracts, and all three required Compatibility Certificates are signed, Resource Development is complete, and The Hit is separately authorized.

## Normative Definitions

- **Acquisition purpose:** exactly `LANGUAGE_CANDIDATE` or `RECORDED_AGENT_PARTICIPATION_CANDIDATE`.
- **Approved repository:** an exact, case-normalized GitHub owner/repository identity present in the active Repository Admission Policy.
- **Approved subtree:** one normalized repository-relative directory recorded for an approved repository. A run may read that directory and its descendants only.
- **Full commit SHA:** exactly forty lowercase hexadecimal characters that GitHub resolves as the requested repository commit. Branches, tags, abbreviated SHAs, pull-request refs, and default-branch inference are not full commit SHAs.
- **Licensed GitHub source:** a source pinned to an approved repository, full child commit SHA, exact single parent commit SHA, child and parent tree SHAs, one unchanged repository-relative path present as a regular file in both commits, child and parent blob SHAs, raw SHA-256 hashes, and approved license evidence.
- **Repository Admission Policy:** the sole acquisition-screening policy. It is immutable and versioned and defines approved repositories, subtrees, purposes, license identifiers, license-file rules, file/path exclusions, safety screens, transport and resource limits, retention rules, and authorization evidence. “License policy” and “screening policy” are sections of this policy, not separate policy classes.
- **Attribution Marker Policy:** an immutable, versioned policy defining accepted vendor-documented authorship, co-authorship, bot identity, or session evidence and the exact normalized classification each marker permits.
- **Approved Policy Register:** an append-only lineage of immutable register versions. Each entry binds one policy class, version, canonical SHA-256 hash, permitted purpose, `valid-from` UTC instant, optional `valid-through` UTC instant, and dated approval by the Don and Rights/Safety Reviewer. Every run and draft binds the exact register-version identifier, register hash, and entry identifier that authorized each policy. A policy absent, not yet valid, expired, or purpose-incompatible at the authoritative receipt time is unauthorized.
- **Revision 7 Compatibility Certificate:** an immutable governance artifact that cites the exact approved Revision 7 path/hash and one unchanged child Contract path/revision/hash, maps every Revision 7 change against that child’s requirements, interfaces, acceptance evidence, and negative scope, records `COMPATIBLE_UNCHANGED` or `REVISION_REQUIRED`, and is signed by the child territory owner and Consigliere. Only `COMPATIBLE_UNCHANGED` permits the child to remain at Revision 1.
- **Operator Authorization Register:** an append-only lineage of immutable register versions. Each entry maps an active named operator to an approved local operating-system identity, acquisition purposes, repository scope, token allowance, valid UTC interval, and least-privilege authorization approved by the Release Operator and Security Reviewer. Every run and draft binds the exact register version/hash and entry identifier.
- **Caller-supplied observation time:** an RFC 3339 UTC instant with whole-second precision used only to make draft content reproducible. It may not be more than five minutes after authoritative receipt time.
- **Authoritative receipt time:** the RFC 3339 whole-second UTC time read from the operator host’s project-approved synchronized system clock at run start. It governs policy validity, retention, and deletion. The first successful GitHub response must contain a valid `Date` value within five minutes of that clock or the run fails before any draft completes.
- **Vendor-documented marker:** an exact marker form supported by a captured vendor document whose publisher, URL, capture date, content hash, applicable product/version, expected Git representation, and permitted classification are recorded in the active Attribution Marker Policy.
- **Verified agent/bot author:** a commit author or committer identity whose GitHub identity, verification state, and vendor-controlled relationship are proven by accepted policy evidence.
- **`NAMED_MODEL_RECORDED`:** accepted evidence durably records a specific model name as participating in the exact code change. The reveal may name only that recorded model.
- **`AGENT_RECORDED`:** accepted evidence durably records an AI coding agent as participating in the exact code change but does not reliably name the underlying model. The reveal shall not infer a model name.
- **`DRAFT_REVIEW_REQUIRED`:** the sole state emitted by acquisition. It is immutable, quarantined, non-playable, non-public, and structurally invalid as publication eligibility or a playable round.
- **Raw snapshot:** encrypted restricted evidence received from GitHub before human review, including commit, tree, blob, license, and marker material.
- **Promotion:** a distinct human-controlled operation that creates a normal H-001 evidence record only after every applicable programme and child requirement is satisfied. Acquisition itself never promotes.
- **Positive provenance candidate:** a changed-code excerpt with accepted `NAMED_MODEL_RECORDED` or `AGENT_RECORDED` evidence bound to the exact parent/child blobs.
- **Negative provenance candidate:** a project-controlled change with affirmative creation-process evidence that no AI coding agent participated. Absence of a public marker is never negative evidence.

## Superseded Programme Clauses

### FR-006 — Provenance Semantics

Revision 6 FR-006 and DEC-005 are replaced as follows:

1. The fixed provenance prompt is: “Is an AI coding agent durably recorded as participating in this code change?”
2. The candidate set has exactly two answers: `RECORDED_AGENT_PARTICIPATION` and `PROJECT_CONTROLLED_HUMAN_ONLY`.
3. A `RECORDED_AGENT_PARTICIPATION` answer requires accepted `NAMED_MODEL_RECORDED` or `AGENT_RECORDED` evidence for the exact change. It does not assert exclusive authorship, line-by-line generation, source quality, or human identity.
4. A `PROJECT_CONTROLLED_HUMAN_ONLY` answer requires project ownership or commission evidence, recorded project authorization, and an affirmative creator/process attestation for the exact change. Missing GitHub attribution, an unfamiliar coding style, or an automated score shall never qualify.
5. Public copy shall describe the observed record, not “AI-written code,” “human-written code,” AI detection, or original authorship.
6. A named model may appear only after authorized reveal and only for `NAMED_MODEL_RECORDED`. `AGENT_RECORDED` reveals use the generic term “AI coding agent.”
7. The two-answer candidate set, candidate count of two, prompt, evidence thresholds, and source regime shall be immutable and frozen before invitations.
8. Stack Overflow is not an active provenance source in Revision 7.
9. Standalone project-authorized model outputs remain historical evidence under FR-016 but are inactive for new Revision 7 provenance rounds because they are not an evidenced code change. Existing synthetic demo items remain development fixtures and do not count toward the beta corpus.
10. The sole active Revision 7 provenance regime is licensed GitHub positive changes versus project-controlled, affirmatively attested human-only changes. Every eligible item is an exact single-parent code change.

### FR-007 — Language Semantics

Revision 6 FR-007 remains binding and gains this source path:

1. A licensed GitHub draft may become a language item only after two independent qualified technical reviewers agree that exactly one candidate is defensible.
2. File extension, GitHub language metadata, or automated detection is only a proposal. Polyglot, embedded-language, generated, ambiguous, or competing-answer material is ineligible.
3. The excerpt remains bound to immutable source, evidence, candidate-set, clue-set, and review versions.

### FR-012 — Content Corpus

Revision 6 FR-012 remains binding. A licensed GitHub item counts toward scheduled or reserve readiness only after promotion through all existing H-001 eligibility gates. A `DRAFT_REVIEW_REQUIRED` artifact never counts.

### FR-016 — Model and Agent Evidence

Revision 6 FR-016 remains binding only for historical separately generated project-authorized model material; such material is inactive for new Revision 7 provenance rounds. For a licensed GitHub positive provenance candidate, the following record is required instead:

1. Preserve the exact commit author, committer, signature/verification result, complete commit message hash, parsed marker, and any accepted vendor session reference.
2. Record the accepted marker-policy rule and classification as `NAMED_MODEL_RECORDED` or `AGENT_RECORDED`.
3. Bind changed lines to a deterministic comparison of the pinned parent and child blobs. GitHub’s displayed patch, truncation-prone patch field, or rendered commit page may be stored only as diagnostic material and shall not decide the excerpt.
4. Require exactly one parent commit and the same regular-file path with text blobs in both parent and child. Root commits, merge commits, added paths, deleted paths, renames, copies, type changes, and binary changes are rejected in the first slice.
5. A provenance excerpt shall contain at least one changed executable or declarative code line after filtering. Dependency-only, comment-only, whitespace-only, generated, vendored, minified, lockfile, documentation, and metadata-only changes are ineligible for provenance gameplay.
6. Record whether the marker permits a named-model claim, a generic-agent claim, or neither. Never upgrade generic agent evidence to a named-model claim and never characterize a conventional trailer as authenticated proof of participation.

### NFR-011 — Acquisition Evidence Security

Revision 6 NFR-011 remains binding and gains these controls:

1. Raw snapshots must be stored outside the repository root, package roots, build contexts, public directories, caches, and temporary directories not owned by the acquisition tool.
2. The configured storage root must be absolute, resolve without symbolic links, reside on a project-approved encrypted volume, and be created with owner-only directory permissions. Every file is owner-only.

5. Secret- or personal-data-bearing rejected payloads shall be deleted immediately after detection and no later than one elapsed hour after receipt. Other rejected raw snapshots shall be deleted within twenty-four elapsed hours.
6. Unresolved draft raw snapshots expire thirty calendar days after acquisition. Promoted or rejected review snapshots expire thirty calendar days after the final review decision. Only hashes, non-sensitive reasons, authorization evidence, and legally required notices may remain afterward.
7. A scoped legal hold may delay deletion only when recorded under the existing data schedule with owner, basis, affected objects, review date, and release action.
8. Retention and deletion deadlines use authoritative receipt time or, for post-review periods, the authoritative final-decision time. Caller-supplied observation time never controls deletion.

### NFR-020 — Operator and Runtime Isolation

1. Acquisition shall exist only under an operator-owned package or operation subpath.
2. Browser, gameplay server, public bundles, source maps, manifests, telemetry, and participant-facing dependency graphs shall contain no acquisition transport, GitHub credential handling, raw snapshot store, policy authorizer, or operator command.
3. The operator command may read a GitHub token from an approved secret input. The token shall never be accepted as a command argument, URL component, persisted configuration value, checkpoint field, diagnostic, or log field.
4. The acquisition package shall not import gameplay delivery code. Promotion uses a narrow reviewed adapter into H-001; gameplay reads only already-approved catalogue output.
5. Every run, resume, rejection, pause, raw-object creation/deletion, draft completion, and promotion handoff requires an active named operator in the Operator Authorization Register and emits an append-only metadata-only audit event bound to that authorization.
6. An authenticated GitHub token, when used, shall be restricted to read-only access to public repository metadata and contents for the approved repositories. A broader token, mismatched operating-system identity, expired authorization, or unauthorized purpose fails before network access.

### NFR-021 — Bounded Transport and Resource Use

1. A run accepts exactly one approved repository, one full commit SHA, one approved subtree, one acquisition purpose, and one caller-supplied observation time. It independently records authoritative receipt time.
2. All network requests use HTTPS to `api.github.com` only. Redirects, alternate hosts, GraphQL, HTML pages, repository archives, Git protocol, and raw-content hosts are excluded.
3. Each request has a fifteen-second timeout. No request is automatically retried. A timeout, transport error, malformed response, redirect, or HTTP error fails closed without producing a complete draft.
4. HTTP 403 or 429 creates a resumable paused checkpoint only when the response includes a valid GitHub rate-limit signal: either remaining quota of zero with a future reset instant, or a positive `Retry-After` duration. Every other 403 and any malformed rate-limit signal is a terminal authorization/policy rejection. Resumption is an explicit operator action after the validated limit permits it.
5. A run may make at most 500 requests, traverse at most 10,000 tree entries, select at most 200 blobs, accept at most 256 KiB per decoded blob, and receive at most 50 MiB across all response bodies. Crossing any limit pauses or rejects the run without weakening prior evidence.
6. At most four requests may be active concurrently.
7. Tree traversal uses pinned non-recursive tree objects rooted at the approved subtree. Every visited tree SHA is checkpointed and verified. Any tree response marked truncated is rejected, regardless of request style.
8. A resumed run revalidates repository, commit, parent, tree, policy, tool, checkpoint, and already-stored object hashes before continuing. Mismatch rejects the checkpoint.

### NFR-022 — Determinism, Safety, and Idempotence

1. Repeating a completed run with identical immutable inputs, policy/register versions, tool version, and caller-supplied observation time shall produce byte-identical draft content. Authoritative run-audit events remain distinct and are not part of deterministic draft bytes.
2. Repeating or resuming a run shall not create a second raw object or draft for the same immutable source identity and hashes.
3. Source bytes are never executed, compiled, imported, rendered as markup, or passed to a model.
4. Line endings normalize deterministically for review while the exact raw-byte hash remains preserved.
5. Path traversal, absolute paths, symbolic links, submodules, binary content, unsupported extensions, generated/vendor/minified content, deceptive controls, secret-like material, suspicious personal data, duplicates, and oversize inputs fail closed with non-sensitive reason codes.
6. Public or operator logs contain identifiers, counts, timings, status, and non-sensitive reason codes only. They contain no token, raw code, commit message, email address, source path beyond an approved redacted form, secret match, or plaintext evidence.

## Architecture Decisions

1. **AD-ACQ-001 — Approach B amendment chain.** Revision 7 authorizes the programme direction; three separately signed child Revision 2 Contracts authorize their respective implementation territories.
2. **AD-ACQ-002 — Narrow hexagonal boundary.** GitHub transport, domain screening, encrypted snapshot storage, and H-001 promotion are separate boundaries with injected interfaces. Domain tests use deterministic in-memory fixtures; only controlled operator rehearsals use the live network.
3. **AD-ACQ-003 — Immutable source reconstruction.** Commit, parent, tree, and blob objects are the evidence base. Changed-code evidence comes from parent/child blob comparison, never from a rendered patch.
4. **AD-ACQ-004 — Policy trust root.** The signed programme and exact Approved Policy Register version/entry authorize the Repository Admission Policy and Attribution Marker Policy hashes. Acquisition rejects an unregistered, altered, not-yet-valid, expired, or purpose-incompatible policy.
5. **AD-ACQ-005 — Quarantine by type and capability.** Acquisition produces only `DRAFT_REVIEW_REQUIRED`; the acquisition package has neither a publication operation nor a playable-round output.
6. **AD-ACQ-006 — Existing review gates remain authoritative.** Automated screening reduces unsafe review work but never creates rights, technical, safety, accessibility, difficulty, provenance, or publication approval.
7. **AD-ACQ-007 — GeoGuessr-for-code continuity.** Both accepted outputs are unfamiliar code locations that players infer from code evidence. The importer is content infrastructure for the shared arcade, not a detached repository-analysis product.
